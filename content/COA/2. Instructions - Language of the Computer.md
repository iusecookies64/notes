### Introduction

To command a computer's hardware, we must speak it's language. The word's in a computer's language are called the *instructions* and the vocabulary is called the *instruction set*.

Different hardware have different *instructions set*, but one might easily think that these different instructions sets will be very different from each other just like how different languages are often very different from each other. But that is not the case, in reality they are very similar, they are more like regional dialects than completely different languages.

Hence, once you learn one, it is easy to pick others. In this chapter we will use the RISC-V set, which was originally developed at UC Berkeley in 2010. Few other examples of instructions set are MIPS (Microprocessor without Interlocked Pipeline Stages) in several respects, RISC-V follows a similar design, Intel x86 architecture originated in 1970.

This similarity of instruction set occurs because all computers are constructed from hardware technologies based on similar principles and because there are a few basic operations that every computer must provide. Moreover computer designers have a common goal, to find a language that is makes it easy to build the hardware and compilers while maximizing performance and minimizing cost and efficiency. This goal is time honored, the following quote was written before you could buy a computer and still holds true to this day as it was in 1947.

>[!Quote]
>It is easy to see by formal-logical methods that there exist certain [instruction sets] that are in abstract adequate to control and cause the execution of any sequence of operations.… The really decisive considerations from the present point of view, in selecting an [instruction set], are more of a practical nature: simplicity of the equipment demanded by the [instruction set], and the clarity of its application to the actually important problems together with the speed of its handling of those problems.
>-- *Burks, Goldstine, and von Neumann, 1947*

### Operations of the Computer

>[!Quote]
>There must certainly be instructions for performing the fundamental arithmetic operations.
>-- *Burks, Goldstine, and von Neumann, 1947*

Every computer must be able to perform arithmetic operations. In the RISC-V language the instruction `add a, b, c` adds the values in variables `b` and `c` and stores the result in `a`. This notation is rigid in that each instruction performs exactly one operations and must have exactly 3 variables.

**Example**
Suppose we want to store the sum of variables `a, c, b, d` in a variable `f`, then the RISC-V assembly code for it would be.

```riscv
add f, a, b  // f = a + b
add f, f, c  // f = f + c
add f, f, d  // f = f + d
```

Thus it takes three instructions to sum 4 variables. The words to the right of double slashes on each line above are ***comments***.

The natural number of operands for an operation like addition is three; the two numbers being added together and a place to put the sum. Requiring every instruction to have exactly three operands conforms to the philosophy of keeping hardware simple: hardware for variable number of operands is more complicated than hardware for a fixed number.

>[!Info] Design Principle 1
>Simplicity favors regularity.

The first hardware design principle simply says that by adhering to regular and predictable structure (of instructions), hardware can be made smaller, faster, and easier to design and build i.e. ***Simpler***.

The core idea is to avoid introducing special cases and complex instructions that require intricate and specialized hardware. Instead a streamlined and consistent approach is favored. This regularity simplifies the process of decoding and executing instructions, which in turn leads to a more efficient and higher-performing processor.

>[!Note]
>The Intel x86 architecture does not follow this design principle it is the classic case of CISC (Complex Instruction Set Computer) architecture.
>
>It has instructions varying anywhere from 1 byte to 15 bytes, it also has irregular instruction formats i.e. the location of opcodes, and addressing modes can vary significantly from one instruction to another.
>
>Hence it requires sophisticated instruction decoding hardware that needs to find what the instructions is and where the current instruction ends and the next instruction starts. This makes the hardware larger and more power-hungry.
>
>Modern x86 processors from Intel and AMD employ a clever trick: they have a complex "front-end" that **translates the complicated CISC x86 instructions into simpler, internal RISC-like micro-operations (µops)**. These µops are then executed by a highly optimized, regular, RISC-style core. For this translation layer is fully hardware based that in real time translated complex instructions to RISC style instructions.
>
>The result of translation is also cached so that we don't have to translate same instruction again. This works really well because most programs spend 90% of their time in 10% of their code.

**Example**
Convert the following high level code to RISC-V instructions `f = (g + h) - (i + j);`.

The each arithmetic operations needs to be done separately and their results needs to be stored in temporary variables.

```riscv
add t0, g, h    // temporary variable t0 = g + h
add t1, i, j    // temporary variable t1 = i + j
sub f, t0, t1   // f = t0 - t1 = (g + h) - (i + j)
```

### Operands of the Computer Hardware

Unlike high level programming languages, the operands of RISC-V arithmetic instructions is restricted; they must be from a limited number of special locations build directly in hardware called called ***registers***. 

The size of register in RISC-V  architecture is 64 bits. Groups of 64 bits occurs so frequently that they are given a special name ***doubleword***. Similarly groups of 32-bits is called ***word*** in RISC-V architecture.

One major difference between variables in programming language and registers is that the registers are very limited in number. In RISC-V the number of registers is typically 32.

>[!Info] Design Principle 2
>Smaller is faster.

There are two main reasons for having the low number of registers. 
- The first is that if the number of registers is large, this will increase the memory read/write time which in turn will affect the clock cycle time and hence overall decreased performance.
- The other reason to keep the number of registers small is the number of bits it would take in the instruction format to specify which registers to use as operands.

Hence the size of registers is chosen in a way that would balance the program's craving for more registers and the designer's desire to keep clock cycles fast at the same time sticking to the principle **Simplicity favors regularity** i.e. keeping instructions consistent.
