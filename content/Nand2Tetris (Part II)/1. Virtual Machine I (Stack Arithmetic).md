### Program Compilation Preview

Consider that we have a code written in a high level language, and now we want to run it on a computer, well we need to translate that high level code to assembly for that computer, this is show below.

![[Pasted image 20250222162219.png]]

Now, let's say we were able to develop a compiler that translates this high level code to assembly code and we are able to run it on the chosen computer.

Here is where we see our first problem i.e. there are many different kinds of computers in this world and we would want our code to work on each of them (well at least most of them). Each of these computer might have different machine languages, and hence we need to create multiple compilers i.e. one for each different architecture.

![[Pasted image 20250222162845.png]]

There are two main ways to approach this problem. The first is we write compilers for each and every machine directly, this is called **Direct Compilation**, the other approach is to compile the code in 2-steps, this is known as **Two-Step Compilation**.

**1. Direct Compilation (Like C/C++, Go, Rust):**

- One big, complex translation step goes straight from the high-level language to the computer's specific instructions.
- This is harder to do, especially if you want the program to run on many different types of computers (like different kinds of phones, PCs, and servers).

**2. Two-Step Compilation (Like Java, C#):**

- This approach uses two steps to make the translation process easier.
- **Step 1: To "Universal" Code:** The programmer's code is changed into a simpler form called "bytecode." Think of bytecode as instructions for a "pretend computer" (called a _virtual machine_). This bytecode is the same, no matter what kind of real computer you'll use later.
- **Step 2: To Real Computer Instructions:** This bytecode is then run by the virtual machine. The virtual machine can do this in two ways:
- **Just-In-Time (JIT) Compilation:** The virtual machine quickly turns the bytecode into the real computer's instructions while the program is running. It's like translating on the fly.
- **Interpretation:** The virtual machine reads and performs each bytecode instruction one at a time.

**Why is the two-step approach often easier?**

You only have to create _one_ translator to go from the high-level code to the "universal" bytecode. Then, you can have smaller, simpler translators that only handle going from the "universal" bytecode to each specific computer's language. The "universal" bytecode is already much closer to how computers think (it talks about things like memory and basic operations), so that second translation is much simpler than translating all the way from the original high-level code. High-level code has a lot of complicated features; those are simplified in the bytecode.

The programming language **Jack** that we are going to build will follow the second approach.

### VM Abstraction: The Stack

VM Abstraction is the architecture of the Virtual Machine. This will tell us what type of operations does it support. This is needed as we need to translate the high level code into these commands.

When deciding on our VM architecture, we have two main objectives,
- The abstraction must be such that it is simple to convert high level commands to VM machine commands. That is we want the distance between high level language and VM machine language as small as possible.
- The abstraction must be low enough that it is simple to convert its command to an actual computer's machine language. That is we want the distance between VM code and final machine code to be minimum.

Over the years, people have settled onto a VM architecture called the **Stack Machine**. It strikes the perfect balance of both the objectives.

![[Pasted image 20250222185621.png]]
#### Stack Machine (Architecture)

The stack machine contains of two types of memories, first is the main memory i.e. the RAM. The second type of memory is something called the Stack Memory.

Unlike the RAM which allows random access to any address, the stack memory works exactly the stack data structure that we all have studied i.e. FIFO. Which means that we can only add values on top of the stack, and we can remove values from the top.

In summary, the stack memory supports the following two commands,
- **push x:** add element x on top of the stack, if x is a number, then we add the number, if x is a memory address, then we add the number stored in that address.
- **pop x:** remove the top most element in the stack and store it in the memory address x.

The stack memory has a stack pointer, which stores the address where the next item will be stored, it moves up and down as we add/remove items to/from the stack.

![[Pasted image 20250222225534.png]]
#### Stack Machine (Commands)

Stack Machine could perform many fundamental operations on the stack memory, below we have listed few of them just to get a feel of what these commands do.
- **add:** This command pops the top 2 values from the stack, then adds them up on the side, then pushes back the result into the stack.
- **neg:** This pops the value, negates it, and pushed it back.
- **eq:** This pops the 2 values, then if they are equal pushed back true, otherwise pushed back false.
- **or:** This pops the 2 values, does logical **or** and puts the result back into the stack.

![[Pasted image 20250222224107.png]]

Now a natural question that might come to your mind is why these commands, what is their use. These commands very elegantly implement expressions written in high level languages.

### VM Abstraction: Memory Segments

In any high level programming language, there are different types of variables i.e. function arguments, static variables, local variables etc. The differentiation between these variables is very important for our programs to run as we intend them to run.

In Stack Machine, this distinction is made using having multiple memories instead of having a single memory, this is shown in the diagram below.

![[Pasted image 20250223134022.png]]

When we look at the high level code, have different kinds of variables. This distinction is also seen in the compiled VM code, where each push/pop command if followed by the memory segment name and then the address in that memory segment.

A thing to note here is that the variable names are lost in this translation, and hence our VM abstraction does not recognise variable names. JVM also does not recognise variable names, hence all of them have to converted to references during translation.

So, we have many memory segments in our Stack Machine as listed below.

**1. Local Segment (`local`)**
- Stores **local variables** of the currently executing function.
- Mapped to the **RAM location pointed to by the LCL register**.
- The VM translates `push local i` into accessing `LCL + i` in RAM.

**2. Argument Segment (`argument`)**
- Stores **function arguments** passed to the currently executing function.
- Mapped to the **RAM location pointed to by the ARG register**.
- The VM translates `push argument i` into accessing `ARG + i` in RAM.

**3. This Segment (`this`)**
- Used to refer to an object’s **fields** (used for object-oriented programming).
- Typically **points to the base address of the current object**.
- Mapped to the **RAM location stored in the THIS register**.
- `push this i` accesses `THIS + i`.

**4. That Segment (`that`)**
- Used similarly to `this`, often for referencing dynamic memory.
- Mapped to the **RAM location stored in the THAT register**.
- `push that i` accesses `THAT + i`.

**5. Constant Segment (`constant`)**
- Represents **immediate values**.
- Not stored in RAM; instead, when executing `push constant i`, the VM **directly loads** the value `i` onto the stack.
- **Note:** We cannot use constant segment using pop command, which is obvious from above definition.

**6. Pointer Segment (`pointer`)**
- Holds two specific addresses:
    - `pointer 0` → stores the address of `this`.
    - `pointer 1` → stores the address of `that`.
- Mapped to **RAM locations 3 and 4**.
- `push pointer 0` retrieves the value stored in `THIS`, and `push pointer 1` retrieves `THAT`.

**7. Static Segment (`static`)**
- Stores **global/static variables**, shared across functions within the same VM file.
- Mapped to **RAM locations 16-255**, unique for each `.vm` file.
- The VM translates `push static i` into `@ClassName.i`, meaning the variable is given a globally unique name based on the file.

**8. Temp Segment (`temp`)**
- Stores temporary values.
- Mapped to **RAM locations 5-12** (fixed region of memory).
- `push temp i` accesses RAM at `5 + i`.

![[Pasted image 20250223143755.png]]

**Example:** Below is vm code that achieves the following task `static 2 = argument 1`

```
push argument 1
pop static 2
```

Any data transfer between the memory segments happens through the stack only.

### VM Implementation: The Stack

So, far we have looked at the stack machine as an abstraction, but now we will start to actually build it. As we know, that the stack machine is not an actual computer, but a virtual computer.

The commands for a stack machine will be run on a Von Neumann Machine i.e. a single memory machine.

Before learning how to implement the stack machine on a Von Neumann Machine, we will first need to know about **Pointers and Pointer Manipulation**.

#### Pointers And Pointer Manipulation

Pointers are nothing but addresses in ram whose value is another address i.e. it's value points to another address, hence the name **Pointer**.

If `p` is a variable which we are treating as a pointer and let's say it's address in memory is `A`, then `p = RAM[A]` and `*p = RAM[RAM[A]]` i.e. using the `*` we can directly the ram address that p points to.

Below are some pseudo assembly codes involving pointers.

![[Pasted image 20250301175129.png]]

Below are the implementations of each of these commands in the Hack Assembly Language.

```asm
// D=*p
@p
A=M
D=M

// p--
@p
M=M-1

// p++
M=M+1
```

These commands are very useful in implementing in the **Stack Machine** as you will see later.
#### Stack Machine

 The stack machine abstraction has a stack memory, a stack pointer and commands push and pop. Let's see how these will be implemented on a Von Neumann Machine.

Since the stack is a memory, it needs to live in our `RAM`, so does the stack pointer. To store the stack pointer, we simply need a ram address in which we will store the stack pointer. For storing the actual values in a stack, we are going to define a base memory in `RAM`, starting which we will have stack elements in consecutive addresses.

We will assume that the stack pointer `SP` lives in `RAM[0]` and the base address for our stack to be `256` i.e. `RAM[0] = 256` initially. The value `256` might seem an arbitrary value, but later we will see that it makes a lot of sense.

##### Implementing `local`

The local memory stores the local variables of a function. Just like the stack, we need to assign some portion of the ram as local memory. In our hack machine the local memory segment starts from the base address `1015`. This value is stored in the `LCL` variable which is `RAM[1]`.

![[Pasted image 20250302140102.png]]

>[!Note]
>Both `sp` and `lcl` are pointer variables, but we are using them in different ways.
>- The value `sp` is the address of were the next pushed value in the stack will go. This keeps on changing.
>- The value `lcl` stores the base address of local memory segment, and remains same during the course of a function call.

Now, let's see how we can implement a command like `pop local i`, it is shown below.

```asm
// in pseudo assembly
addr = lcl + i
sp--
*addr=*sp

// in hack assembly
@i
D=A
@lcl
D=M+D          // storing target address i.e LCL + i

@addr
M=D            // storing target address in addr

@SP
AM=M-1         // sp--
D=M            // D=*sp (pop value)

@addr
A=M
M=D            // store the popped value in target address
```

>[!Note]
>Consider the stack looks like [12, 5, ., ., ] i.e. it has two values and `sp` points at the third address. Now lets say a `pop` command is executed, this will decrease `sp` by `1` i.e. pointing at the second position. 
>
>In this case we say that the value `5` is dead, even if it is present in the stack. But due to the fact that the stack pointer has moved down, the next time something is pushed, this value will be overwritten.
>
>This is usually the case when dealing with stack, at any given moment, there may be a lot of garbage values, but the stack pointer helps differentiate what is garbage and what is useful.

Similarly, for the command `push local i`, the pseudo code is `addr=LCL+i, *SP=*addr, SP++`, this pseudo code can be implemented in the hack in similar way as done for the `pop` command. 
##### Implementing `argument`, `this`, `that`

Memory segments like `local`, `argument`, `this` and `that` are all similar. The `argument` stores the arguments of the current function, the `this` stores the member variables of an object (in object oriented programming). And `that` stores some dynamic memory like arrays etc.

Operating on them is similar to how we operate on `local`, this is shown below.

![[Pasted image 20250302144918.png]]

>[!Note]
>We see that the values of pointers `lcl, this, that, arg` can be anything, and the code will still work the same. What values these get is decided by the compiler and operating system.

##### Implementing `constant`

The constant segment simply gives the constant value that is asked for, it is a virtual memory segment. We can only push values from this segment, but not pop values into this segment.

The command `push constant i` can be implemented using `*sp=i, sp++`.
##### Implementing `static`

The static memory segment is a segment that contains variables that are accessible throughout the program and common to every function.

To implement static variables we will use a feature of the hack assemble, which is how it deals with variables.

Let's say we are translating a vm code written in a file called `Foo.vm` and we encounter a command like `push/pop static i`, then we will convert this command to `@Foo.i` followed by commands for `push/pop`.

In short we are creating a variable called `Foo.i` that will be mapped to some location in ram between `RAM[16]...RAM[255]` based on the variable's position in the assembly code.

This will be done by the assembler as this is a feature, then these variables will remain there as this throughout the life of the program and can be shared by any function/method.

Below is the implementation of `push/pop static i`.

```asm
// Assumption: reading vm code from a file called Foo.vm

// push static i
@Foo.i
D=M      // storing value of static i in D
@SP
A=M
M=D      // RAM[sp] = static i
@SP
M=M+1

// pop static i
@SP
AM=M-1   // sp--
D=M      // storing top value of stack in D
@Foo.i
M=D
```

>[!Note]
>So far we our implementations of memory segments were platform independent. But the implementation of static memory segment uses a feature of the hack assembly language.

##### Implementing `pointer`

The pointer memory segment is very obscure, that is we only understand why we need it, when we start writing the compiler.

This memory comes into use when translating high level method code into vm code. The compiler generates code that keeps track of the base addresses of the `this` and `that` segments using the `pointer` segment.

The only allowed `pointer` commands are `push/pop pointer 0/1`. Here `0` is for accessing the `this` pointer and `1` is for the `that` pointer.

Below are pseudo assembly codes that realise the pointer commands.

```asm
// push pointer 0/1
*SP = THIS/THAT, SP++

// pop pointer 0/1
SP--, THIS/THAT = *SP
```
